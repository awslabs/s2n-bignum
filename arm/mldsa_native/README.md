# Compiled code from mldsa-native

This directory contains AArch64 code compiled from the portable C
implementation in [mldsa-native][1], transcribed from pre-built binaries,
and the scripts that produce and check the files the proofs in
`../proofs/mldsa_native` use. As for `../mlkem_native`, the aim is to
verify compiler-generated rather than hand-written code; the code here is
only used for the proofs and is not part of the library.

[1]: https://github.com/pq-code-package/mldsa-native

Unlike the mlkem-native proofs, which are proved against FIPS 203, the
mldsa-native proofs are proved function by function against a functional
specification that follows the C code: `../../common/mldsa_native_*.ml`
defines, for each C function, the HOL function on machine words that it
computes. Composed, these give one version of ML-DSA; relating it to
FIPS 204 is a separate step that does not involve the compiled code (see
"Relation to FIPS 204" below).

## Organization

The files for each build of the binary are in directories named after the
compiler and the optimization level, `<build>` = `<compiler>_<level>`,
e.g. `gcc12_O2` for the gcc 12 `-O2` binary, followed by the layout and
the configuration if they are not the default ones:
`gcc12_O2_reduced_ram` is the gcc 12 `-O2` binary built with
`MLD_CONFIG_REDUCE_RAM`, and `clang23_O3_mono_reduced_ram` the clang 23
`-O3` binary of the monolithic layout built with it (see their
`README.md`). For a build:

 - `<build>/libmldsa.S` is the transcription of the whole image of the
   binary, generated by `gen_libmldsa_s.py`;
 - `../proofs/mldsa_native/<build>/layout.ml`, generated by
   `gen_layout.py`, gives names to the addresses in the binary;
 - `../proofs/mldsa_native/<build>/libmldsa.ml` defines the image;
 - `../proofs/mldsa_native/<build>/<f>_spec.ml` states the theorems for
   the function `<f>` (assumed with `assume_spec`, see
   `../proofs/mlkem_native/relative.ml`) and `<f>_proof.ml` proves them,
   relative to the statements of its callees;
 - `../proofs/mldsa_native/<build>/fips204.ml`, `fips204_sign.ml` and
   `fips204_verify.ml` restate the CORRECT theorems of the API functions
   with the FIPS 204 specification `../../common/fips204/fips204.ml`, and
   `fips204_safe.ml` states their SAFE theorems without the hypotheses
   that the samplers terminate (see below);
 - `<build>/proofs.mk`, generated by `../../tools/native_proofs_mk.py
   mldsa_native <build>` from the
   `needs` of the proofs, lists the transcriptions and proofs for
   `../Makefile`, which includes it.

`../../tools/native_link.py mldsa_native <build>` generates the link file
of a build, which loads all
proof files and then the FIPS 204 files in one session and discharges the
assumed statements of the callees.

Functions whose code is the same for all parameter sets, such as
`mldsa_poly_add`, have files named after the function without the
namespace (`poly_add_spec.ml`), and those of one parameter set have the
suffix `_44`, `_65` or `_87`.

The scripts here are adapted copies of those in `../mlkem_native`, with
the names of the library and of its namespace changed. `gen_layout.py`
also replaces the dots in the names of data symbols (`oid_map.0` gives
`rodata_oid_map_0`). The lemmas and tools that do not depend on the
instruction set are in `../../common/fips204/properties/mldsa_native*.ml`,
shared with the x86 proofs; `../proofs/utils/mldsa_native*.ml` has the
AArch64 parts.

## Source of the code

The code is transcribed from the disassembly of the pre-built binaries
made by `scripts/build-binaries` of mldsa-native from its commit
`d38418ea3d4c`, as recorded in `binaries/builds.json` of the `binary`
branch there (commit `65f9995`, "binaries: Rebuild the AArch64 matrix from
main"), which has the binaries of all three builds. We use the
"multilevel" build (`examples/multilevel_build`), compiled with `CFLAGS`
set to `-O<level> -g -gdwarf-4 -gsplit-dwarf -fPIC`, with `AUTO=0` and
without the native backends. In this build the code shared by the three
parameter sets is compiled once, with the namespace `mldsa_`, and the
rest once per parameter set, with the namespaces `mldsa44_`, `mldsa65_`
and `mldsa87_`.

| File                           | Compiler   | Binary                                   |
|--------------------------------|------------|------------------------------------------|
| gcc12_O2/libmldsa.S            | gcc 12.3.0 | binaries/multilevel/gcc12/O2/libmldsa.so |
| gcc12_O2/keccakf1600_permute.S | gcc 12.3.0 | binaries/multilevel/gcc12/O2/libmldsa.so |
| gcc12_O2_reduced_ram/libmldsa.S | gcc 12.3.0 | binaries/reduced-ram/multilevel/gcc12/O2/libmldsa.so |
| gcc12_O2_reduced_ram/keccakf1600_permute.S | gcc 12.3.0 | binaries/reduced-ram/multilevel/gcc12/O2/libmldsa.so |
| gcc12_Os/libmldsa.S            | gcc 12.3.0 | binaries/multilevel/gcc12/Os/libmldsa.so |
| clang23_O3_mono_reduced_ram/libmldsa.S | clang 23.1.3 | binaries/reduced-ram/multilevel-mono/clang23/O3/libmldsa.so |

The reduced-RAM build is compiled with `-DMLD_CONFIG_REDUCE_RAM` in
addition, from the same source and the same `binary` branch of
mldsa-native; see
`gcc12_O2_reduced_ram/README.md` for its source and how it differs.
The clang23_O3_mono_reduced_ram build is the same configuration compiled
by clang 23 with `-O3` as one translation unit (the monolithic layout,
`examples/monolithic_build_multilevel`), from the same source and the same
`binary` branch; see `clang23_O3_mono_reduced_ram/README.md` for its
source, how it differs and how the inlined code is proved.

The gcc12_Os build is the default configuration compiled with `-Os`, from
the `binary` branch of mldsa-native; see `gcc12_Os/README.md` for its
source, how it differs and which functions it proves. It has no separate
transcription of `mldsa_keccakf1600_permute`: that function is proved in
the image itself, with the proof of the same code in the gcc12_Os image of
mlkem-native.

`gcc12_O2/keccakf1600_permute.S` is the code of `mldsa_keccakf1600_permute`
alone, with its table of round constants as a separate symbol: the code
is byte-for-byte that of `mlkem_keccakf1600_permute` in the gcc 12 -O2
build of mlkem-native, and so its proof is that of
`../proofs/mlkem_native/gcc12_O2/keccakf1600_permute_proof.ml`, on the
separate object, transferred to the image. The other Keccak functions are proved
in the image directly, also with the proofs of the same code in
mlkem-native. `../mlkem_native/check_transcription.py` checks the
separate object against the binary:

```
python3 mlkem_native/check_transcription.py \
  mldsa_native/gcc12_O2/keccakf1600_permute.o \
  mldsa_native_keccakf1600_permute_gcc12_O2 \
  <mldsa-native>/binaries/multilevel/gcc12/O2/libmldsa.so \
  mldsa_keccakf1600_permute \
  mldsa_native_keccakf1600_permute_gcc12_O2_rc mld_KeccakF_RoundConstants
```

The SHA-256 hash of the binary used, which matches that recorded in
`binaries/SHA256SUMS` of mldsa-native, is:

```
binaries/multilevel/gcc12/O2/libmldsa.so
  37d12a5bf9ae1a5c8a06d8224147eaafcd78d42aad5d5ca242c9f461e907f69b
```

To regenerate the files of the build, in the `arm` directory:

```
python3 mldsa_native/gen_libmldsa_s.py \
  <mldsa-native>/binaries/multilevel/gcc12/O2/libmldsa.so \
  mldsa_native_libmldsa_gcc12_O2 "gcc 12, -O2" \
  binaries/multilevel/gcc12/O2/libmldsa.so $PWD/../include \
  > mldsa_native/gcc12_O2/libmldsa.S
python3 mldsa_native/gen_layout.py \
  --name multilevel/gcc12/O2/libmldsa.so \
  <mldsa-native>/binaries/multilevel/gcc12/O2/libmldsa.so \
  > proofs/mldsa_native/gcc12_O2/layout.ml
python3 ../tools/native_proofs_mk.py mldsa_native gcc12_O2 \
  > mldsa_native/gcc12_O2/proofs.mk
```

`gen_libmldsa_s.py` assembles the transcription and checks that it is
byte-for-byte the image of the binary, from address 0 to the end of the
read-only data, writing any instruction that the assembler would encode
differently, and every ADR and ADRP, as `.inst`. `libmldsa.ml` checks
that the image has the size given in the layout file.

## What is proved

For each of the 192 functions of the gcc12_O2 image (176 for the
reduced-RAM one, 206 for the gcc12_Os one and 67 for the clang 23 one),
`<f>_proof.ml` proves three theorems about its code: the leaf functions,
the polynomial and vector functions, the samplers, the packing functions,
the top-level functions and the API functions.

 - `..._FULL`: `?f_events. !e args. H ==> ensures arm (P /\ events = e)
   (Q /\ ?e2. events = APPEND e2 e /\ e2 = f_events <public args> /\
   memaccess_inbounds e2 R W) C`. This combines three properties.
   Correctness: the postcondition Q, with the functional specifications
   of `common/mldsa_native_*.ml`. Constant time: the trace of memory
   addresses and branch targets of the execution is a fixed function
   f_events of the public arguments only. Memory safety: all loads are
   within the regions R and all stores within W.
 - `..._CORRECT`: `!args. H ==> ensures arm P Q C`, derived from FULL.
 - `..._SAFE`: FULL without Q, in the form of s2n-bignum's other safety
   theorems, derived from FULL.

FULL is the primary theorem because the callers that branch on the
results of their callees need both the values and the events of their
callees at once. These are signing, verification and the samplers.

`link.ml`, generated by `native_link.py`, runs all the proofs and the FIPS
204 files (see below) in one session and closes the theorems of the API
functions and of the FIPS 204 files, so that they have no assumptions.
It runs the proof files as independent jobs; the FIPS 204 files are
loaded after the jobs. In `..`, `make mldsa_native/<build>/link.correct`
checks a build. With the parallel backend of `../../common/par.ml` (see
"Running proofs in parallel" in `../../README.md`, which also gives the
reference configuration and the run times) and `S2N_PAR_DOMAINS=N`, it
runs N jobs at a time, the costliest first,
as given by `link_costs.tsv` of the build, which
`python3 ../tools/link_costs.py mldsa_native <build> [LOG]` updates.
As in mlkem-native, the proofs whose code has two cases for the
alignment of the stack pointer prove the two cases at the same time
with `PAR_THENL`, and the signing functions prove their parts at the
same time.

### The public arguments of the events

Besides addresses, lengths (of messages and contexts), pc and the return
address, the events may depend on exactly what the C code declassifies
(`MLD_CT_TESTING_DECLASSIFY`) or treats as public. These are given as
named HOL functions of the inputs:

 - the matrix A and anything derived from rho (rej_uniform,
   poly_uniform, poly_uniform_4x, polyvec_matrix_expand_eager,
   pk_from_sk's rho);
 - which nibbles the eta samplers accept (`mld_rej_eta_declass`,
   `mld_poly_uniform_eta_declass`, `mld_keypair_declass`);
 - the challenge seed c~ (poly_challenge and, per attempt, signing);
 - per signing attempt, the result of each norm check up to the first
   that fails and, if all pass, w0 - c s2 + c t0 and w1 packed
   (`mld_sign_attempt_declass`); also the number of attempts and the
   signature;
 - for verification, all its inputs (pk, the signature, the message);
 - for pk_from_sk, rho and the result of the check of the key.

## Trusted base

The theorems depend on the following, which the proofs do not establish.
`../../SOUNDNESS.md` discusses the gaps of s2n-bignum's proofs in general.

 - HOL Light's kernel and the OCaml that runs it. Every proof run ends with
   HOL Light's `check_axioms ()` (called by `../../tools/build-proof.sh`),
   which fails if the session has an axiom besides HOL Light's own three.
   `../../common/relative.ml` forms the theorems of a link file with kernel
   rules: `assume_spec` uses `ASSUME`, and `relative_close` discharges each
   assumption with `PROVE_HYP` and fails if one is left. With `HOL_PAR=1`,
   the kernel must also be sound when called from several domains (see
   "Running proofs in parallel" in `../../README.md`).
 - The model of AArch64: `../proofs/arm.ml`, `../proofs/instruction.ml` and
   `../proofs/decode.ml`, which give the semantics
   of the instructions and decode machine code to instructions, and, for
   the theorems of constant time and memory safety, the events that the
   semantics emits (`../../common/safety.ml`). The model is tested, not
   proved, against other implementations of the instructions (see B1 in
   `../../SOUNDNESS.md`).
 - That the machine code proved is the machine code of the binary. The
   proofs are about the code in `<build>/libmldsa.S` and in
   `<build>/keccakf1600_permute.S`, as assembled into the `.o` files by
   `../Makefile`. `gen_libmldsa_s.py` checks that the assembled whole-image
   transcription is byte for byte the image of the pre-built `libmldsa.so`
   when it writes it, and `../mlkem_native/check_transcription.py` compares
   `keccakf1600_permute.o` with the binary; the second is run by hand
   against a checkout of mldsa-native, and neither `make` nor CI runs
   either. That the binaries are built from the mldsa-native sources named
   in "Source of the code" is taken from `binaries/builds.json` and
   `binaries/SHA256SUMS` of mldsa-native; nothing here rebuilds them.
 - The specifications. The theorems about the code (`..._FULL`, `..._CORRECT`
   and `..._SAFE`) state results with the functional specification of each
   C function in `../../common/mldsa_native_*.ml`. The `..._FIPS204`
   theorems state the results of the API functions with FIPS 204 in
   `../../common/fips204/fips204.ml` and FIPS 202 in
   `../../common/fips202/fips202.ml`, which are written by hand (see
   "Relation to FIPS 204" for their hypotheses). A second model of
   FIPS 204, compiled from the pseudocode of the standard, is proved equal
   to `fips204.ml` for key generation, signing and verification, with and
   without pre-hashing, for ML-DSA-44, -65 and -87
   (`../../common/fips204/generated/core/README.md`), so an error in the
   specification would have to be in both. That README says what is not
   covered: neither model is checked against the text of FIPS 204, and the
   statements assume that the random generator does not fail and that
   messages are whole bytes (except the pre-hash of HashML-DSA).
 - Which values the events of a call may depend on: those listed under "The
   public arguments of the events". A reader has to agree that they are
   public.
 - The behaviour of the C library functions and of randombytes, whose code
   is not in the image: the contracts under "Hypotheses".

## Hypotheses

The theorems for the API functions (the `..._FULL`, `..._CORRECT` and
`..._SAFE` theorems of the link file) have these hypotheses; the link file
discharges all others.

 - The image is loaded at a 4096-aligned pc and fits in the address space,
   and the stack pointer is 16-aligned. For the clang23_O3_mono_reduced_ram
   build, the stack pointer is also at least 33792 (32768 for
   `keypair_internal`, `pk_from_sk`, `signature_internal` and
   `verify_internal`) and below 2^63, which decides the comparisons of
   their stack probes, and the 12 pointers to the entries of `oid_map`
   that the loader relocates, which are outside the image, point to them
   (see `clang23_O3_mono_reduced_ram/README.md`).
 - The written regions are disjoint from each other, from the inputs and
   from the image.
 - The function does not write the stack protector guard.
 - Each theorem assumes the contracts of the C library functions that its
   function or the functions it calls use. memset, memcpy and randombytes
   satisfy them through their GOT entries: `memset_full_contract` (in
   `../proofs/utils/mlkem_native_libc_full.ml`) or
   `memset_ret_full_contract`, `memcpy_full_contract` (both in
   `../proofs/utils/mldsa_native_libc.ml`) and `randombytes_safety_contract`
   (in `../proofs/utils/mlkem_native_libc.ml`). Each is a contract for
   correctness and for constant time and memory safety together. A contract
   is about the function at the address that the caller reads from the GOT,
   and holds in every state in which the region (ea,el) holds `ev`. The
   functions are in that one region, which holds their code and data and
   which the caller does not write. They return to the address in X30 and
   change only the registers that the ABI allows and X18 and X30, and no
   memory except the output buffer. So they use no stack. memset sets the
   `len` bytes at `dst` to the low byte of `c`; `memset_ret_full_contract`
   also returns `dst`, as the C standard says, which `mld_sig_unpack_hints`
   uses. memcpy copies `len` bytes from `src` to `dst`; the two buffers do
   not overlap. randombytes writes `len` bytes at `buf`, and neither the
   bytes nor the value that it returns are constrained: it may return any
   bytes, or fail (the code then returns `MLD_ERR_RNG_FAIL`, which the model
   has no counterpart for). The events of a call are a function of its
   arguments and return address, and the call reads only its argument
   buffers and the region (ea,el) and writes only its output buffer.
 - Termination of the rejection samplers and of SampleInBall is not
   assumed by the FIPS 204 theorems (`mldsa_native_fips204_*` and
   `gcc12_O2/fips204*.ml`):
   `../../common/fips204/properties/mldsa_native_fips204_terminates.ml`
   proves the predicates `mld_matrix_terminates`,
   `mld_keypair_terminates_XX`, `mld_poly_challenge_terminates` and
   `mld_sign_terminates_XX` from the fact that Keccak-f[1600] is a
   permutation (`../../common/fips204/properties/terminates.ml`). The
   contracts of the C functions themselves (the `_spec.ml` files) still take
   them as preconditions, and so does `mld_rej_uniform_terminates` of
   `mld_poly_uniform`; `MLD_FIPS204_DISCHARGE` removes them when a
   FIPS 204 theorem uses such a contract. For the SAFE theorems of the
   API functions, `<build>/fips204_safe.ml` does the same: each
   `..._SAFE_FIPS204` is a SAFE theorem with them discharged, as each
   `..._SAFE_FIPS203` of mlkem-native is.
 - Signing makes at most maxatt = (65535 - l) DIV l attempts (16382,
   13106 and 9361), and otherwise returns
   `MLD_ERR_SIGN_ATTEMPTS_EXHAUSTED`.

## Relation to FIPS 204

`common/fips204/fips204.ml` is a mathematical specification of ML-DSA (FIPS
204), and `common/fips204/properties/fips204_properties.ml` proves its
properties. Among them is
the equivalence with the alternative way of checking the low bits and
computing the hints of Section 5.1 of the Round 3 Dilithium
specification, which FIPS 204 permits and mldsa-native uses
(`MLDSA_SIGN_MU_ALT`). The lemmas of
`../../common/fips204/properties/mldsa_native_fips204_*.ml`, shared with
the x86 proofs, relate the specification of the C code to FIPS 204, with no
machine code involved:

 - `_ntt`: the NTT, its inverse and the Montgomery products as
   operations of R_q;
 - `_sample`: SHAKE, ExpandA, RejBoundedPoly, ExpandMask and
   SampleInBall;
 - `_round`: reduce32, Power2Round, Decompose, UseHint, the hints and
   the norm checks;
 - `_pack`: the bit packings, HintBitPack and HintBitUnpack;
 - `_keypair`: the keys of key generation are those of
   `mldsa_keygen_internal` (`MLD_FIPS204_KEYPAIR_44` etc.);
 - `_pk_from_sk`: the public key computed from a secret key is
   pkEncode(rho, t1) for skDecode(sk). The check passes iff s1 and s2
   are within [-eta,eta], t0 matches and tr = H(pk). In particular,
   pk_from_sk accepts the secret key that key generation makes and
   recovers its public key (`MLD_FIPS204_PK_FROM_SK_KEYGEN_44` etc.);
 - `_sign`: signing is FIPS 204 signing (`MLD_FIPS204_SIGN_44` etc.);
 - `_verify`: verification is FIPS 204 verification
   (`MLD_FIPS204_VERIFY_44` etc.).

`../proofs/mldsa_native/gcc12_O2/fips204.ml` (and the same files of
the other builds) derives these from the
lemmas and the CORRECT theorems. For each API function and parameter
set, a theorem `..._FIPS204` states the function with the FIPS 204
functions, with its inputs and outputs as byte strings:
`mldsa_keygen_internal` and `mldsa_keygen` for key generation,
`mldsa_sign_internal`, `mldsa_sign_mu`, `mldsa_sign` and
`hash_mldsa_sign` for signing, and `mldsa_verify_internal`,
`mldsa_verify_mu`, `mldsa_verify` and `hash_mldsa_verify` for
verification. They have two further hypotheses:

 - Signing equals FIPS 204 signing when the fields of s2 in the secret
   key are at most 2 * eta. This holds for every key made by key
   generation. For a malformed key, FIPS 204 can accept an attempt that
   the code rejects (mldsa-native does not check the key when signing).
 - The result of the code is the outcome of the FIPS 204 function, with
   the return codes of `mldsa_native.h` for its cases
   (`common/mldsa_native_errors.ml`). Signing returns an
   `mldsa_sign_result` (`MLDSA_Sign_Success`, `MLDSA_Sign_Error_BadContext`
   for a context of more than 255 bytes, and
   `MLDSA_Sign_Error_OutOfAttempts`) and verification an
   `mldsa_verify_result` (`MLDSA_Verify_Success`,
   `MLDSA_Verify_Error_InvalidSignature` and
   `MLDSA_Verify_Error_BadContext`). `mld_sign_status` and
   `mld_verify_status` map them to `MLD_OK`, `MLD_ERR_INVALID_ARG`,
   `MLD_ERR_SIGN_ATTEMPTS_EXHAUSTED` and `MLD_ERR_INVALID_SIGNATURE`.
   As the code makes at most maxatt attempts, the theorems for signing
   pass the bound `SOME maxatt` to the signing functions, which then make
   the same number of attempts; with `NONE` they search without limit, as
   FIPS 204 does. `MLD_ERR_RNG_FAIL`, when the random generator fails,
   has no counterpart in the model, which has the randomness as an
   argument.
