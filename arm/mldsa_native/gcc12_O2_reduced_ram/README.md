# The gcc 12 -O2 reduced-RAM build

This directory is for mldsa-native's `libmldsa.so` built like the gcc 12
`-O2` one (see `../README.md`), but with `-DMLD_CONFIG_REDUCE_RAM`:
`binaries/aarch64/reduced-ram/multilevel/gcc12/O2/libmldsa.so` in the
`binary-v2.1` branch of mldsa-native (commit `c817bc7df`, "binaries:
Build the ML-DSA v2.1.0 matrices"), built from the v2.1.0 release
(commit `c9999d775`), which is also the source of the gcc12_O2 build.
`libmldsa.S` transcribes its image, from address 0 to the end of the
read-only data at `libmldsa_size` = 0xabc0, and
`../../proofs/mldsa_native/gcc12_O2_reduced_ram/` has its layout
(generated by `../gen_layout.py`), the definition of the image and the
proofs.

The SHA-256 hash of the binary, which matches that recorded in
`binaries/SHA256SUMS` of mldsa-native, is:

```
binaries/aarch64/reduced-ram/multilevel/gcc12/O2/libmldsa.so
  16c5502d0bc71e1210733b6d6192342d92179cd68ef56295f15b079c94e2398e
```

To regenerate the files of the build, in the `arm` directory:

```
python3 mldsa_native/gen_libmldsa_s.py \
  <mldsa-native>/binaries/aarch64/reduced-ram/multilevel/gcc12/O2/libmldsa.so \
  mldsa_native_libmldsa_gcc12_O2_reduced_ram "gcc 12, -O2, reduced RAM" \
  binaries/aarch64/reduced-ram/multilevel/gcc12/O2/libmldsa.so $PWD/../include \
  > mldsa_native/gcc12_O2_reduced_ram/libmldsa.S
python3 mldsa_native/gen_layout.py \
  --name aarch64/reduced-ram/multilevel/gcc12/O2/libmldsa.so \
  <mldsa-native>/binaries/aarch64/reduced-ram/multilevel/gcc12/O2/libmldsa.so \
  > proofs/mldsa_native/gcc12_O2_reduced_ram/layout.ml
python3 ../tools/native_proofs_mk.py mldsa_native gcc12_O2_reduced_ram \
  > mldsa_native/gcc12_O2_reduced_ram/proofs.mk
python3 ../tools/native_link.py mldsa_native gcc12_O2_reduced_ram \
  > proofs/mldsa_native/gcc12_O2_reduced_ram/link.ml
```

`keccakf1600_permute.S` is the separate transcription of
`mldsa_keccakf1600_permute`, as for gcc12_O2.

## Compared with gcc 12 -O2

With `MLD_CONFIG_REDUCE_RAM`, signing, verification and key generation
keep less on the stack: the matrix A is not expanded in full but each
entry is sampled from rho when a product needs it, y is sampled one
polynomial at a time (and sampled again for z), and s1, s2 and t0 stay
packed in the secret key and are unpacked one polynomial at a time where
they are used. The image has 176 functions against 192:

 - 149 have the same code as at gcc12_O2, up to the addresses;
 - 13 have different code: `mld_compute_pack_t0_t1{44,65,87}`,
   `mldsa{44,65,87}_signature_internal`, `mldsa{44,65,87}_verify_internal`,
   `mldsa{44,65,87}_unpack_sk` (which returns pointers into the
   secret key) and `mldsa_shake256x4_absorb_once` (into which
   `mld_keccak_absorb_once_x4` is inlined);
 - 14 are new: `mldsa{44,65,87}_polyvec_matrix_expand_lazy` (the copy of
   rho into the structure of the matrix),
   `mldsa{44,65,87}_polyvec_matrix_pointwise_montgomery_row_lazy` (a row of
   A times a vector), `..._yvec_lazy` (A y, with y sampled on demand),
   `mldsa{44,65,87}_polyveck_reduce` and
   `mldsa{44,87}_poly_uniform_gamma1`;
 - 30 are gone: the eager expansion of the matrix and its products, the
   x4 samplers (`mldsa_poly_uniform_4x`, `poly_uniform_gamma1_4x`, the
   SHAKE128 x4 functions), `polyveck_ntt`, `polyveck_unpack_eta`,
   `polyvecl_pointwise_acc_montgomery`, `polyvecl_uniform_gamma1` and
   `mld_keccak_absorb_once_x4`.

The only instructions that the gcc12_O2 code does not use are LDURH and
STURH.

## The proofs compared with gcc 12 -O2

The proofs of the 149 functions with the same code are those of gcc12_O2
with the names of the build, and where a function's frame or those of its
callees differ, with the offsets of the frame (`keypair_internal`,
`pk_from_sk`, `poly_uniform_eta_4x`, the API functions). The other
functions have new proofs with the same structure: the FULL theorem
(correctness, constant time and memory safety), CORRECT and SAFE. The
statements of the API functions and of their callees up to signing,
verification and key generation are those of gcc12_O2, up to the names and
the stack sizes, so that `fips204.ml`, `fips204_sign.ml` and
`fips204_verify.ml` are those of gcc12_O2 with these changes.

The lazy products reduce each product of a matrix entry and a polynomial
before adding it, where the eager code adds the products and reduces
once. Their results are therefore different words, equal mod q, and only
the final values, made nonnegative by caddq, are the same.
`../../../common/mldsa_native_lazy.ml` defines what the new functions
compute (`mld_polyvec_matrix_row_lazy`, `mld_polyvec_matrix_yvec_lazy`,
`mld_compute_t_lazy`). `lazy_eq_spec.ml` states, and `lazy_eq_proof.ml`
proves (with `../../../common/fips204/properties/mldsa_native_lazy.ml`),
that these give the values of the gcc12_O2 specifications: t
(`mld_compute_t`), w after caddq (`mld_sign_w`) and the rows of the
verification (`mld_verify_internal_ok`), from the congruences mod q of the
NTT domain
(`../../../common/fips204/properties/mldsa_native_ntt_cong.ml`) and the
bounds on the coefficients: those of the unpacked secret key and z, of the
NTTs and of the pointwise products. The proofs of the callers use these
statements as contracts (see `../../../common/relative.ml`), and `link.ml`
closes them with `lazy_eq_proof.ml`.

The events have the same public arguments as for gcc12_O2: the entries of
the matrix are sampled from rho, which is public, and y from rho'', as in
the eager code.

Signing is proved in parts, as for gcc12_O2 (the loop over z, the rows,
the packing of c~ and the hints, the cleanup and the start of an attempt,
then one attempt and the loop over the attempts), with the parts rewritten
for the frame and buffers of the reduced code, whose register allocation
differs between the three parameter sets. The statements of signing keep
the memcpy contract of gcc12_O2, although the reduced code no longer calls
memcpy.
