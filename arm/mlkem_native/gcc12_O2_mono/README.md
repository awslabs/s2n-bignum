# The gcc 12 -O2 monolithic build

This directory is for mlkem-native's `libmlkem.so` built with gcc 12 and
`-O2` as one translation unit:
`binaries/multilevel-mono/gcc12/O2/libmlkem.so` in the `binary` branch of
mlkem-native, compiled from
`examples/monolithic_build_multilevel/mlkem_native_all.c`, which includes
all of mlkem-native for the three parameter sets (see
`binaries/builds.json` there). The gcc12_O2 build is the same source and
compiler, but compiles each source file separately.

`libmlkem.S` transcribes the image, from address 0 to the end of the
read-only data at `libmlkem_size` = 0x5ee0, and is the same as the binary
byte for byte. `../../proofs/mlkem_native/gcc12_O2_mono/` has its layout,
generated by `../gen_layout.py --dwarf`, and the definition of the image.
All 2878 distinct instructions of the image are decoded by the model.

## Compared with the gcc 12 -O2 build

Since the compiler sees all of mlkem-native at once, it inlines much more:

 - The image has 60 functions with code (83 symbols, since some functions
   have several names, e.g. after identical code folding), against 116.
 - 72 of the functions of the gcc 12 -O2 build have no code of their own.
   They are inlined into their callers: all `mlkem*_poly*` and
   `mlkem*_polyvec*` wrappers, `mlkem*_indcpa_dec`, the Keccak and
   SHAKE128 functions other than SHA3 and SHAKE256, and others.
   `mlkem_shake128_init` and `mlkem_shake128x4_init` leave no code at all.
 - The arithmetic and coding kernels stay out of line under the names of
   their static C implementations, e.g. `mlk_poly_ntt_c` for what
   `mlkem_poly_ntt` is in the gcc 12 -O2 build, and the inlined wrappers
   call them.
 - 22 functions have the same code as a function of the gcc 12 -O2 build,
   up to addresses: `mlk_poly_frombytes_c` (as `mlkem_poly_frombytes`),
   `mlk_poly_decompress_d4_c`, `mlk_polyvec_basemul_acc_montgomery_cached_c512`,
   `mlk_rej_uniform_c.constprop.0`, `mlkem_poly_frommsg`, the three
   `gen_matrix` other than `mlkem768_gen_matrix`, and the top-level
   `check_sk`, `enc`, `enc_derand`, `keypair` and `keypair_derand` of all
   three parameter sets. The other 38 differ.

So most of the functions that the proofs of the gcc 12 -O2 build are about
exist here only as inlined code, inside the functions that call them.

## Symbols and debug information

The symbol table still covers all the code: every instruction of `.text`
is in a function symbol, except NOPs that pad functions to 16 bytes. So
the functions, their sizes and the labels that come from the control flow
need no debug information, as for the other builds.

What the symbol table cannot give is where the inlined functions are. This
is in the split debug information (`libmlkem.so.dwp`), which
`../gen_layout.py --dwarf` reads with `../dwarf_inline.py`: labels
`<f>_in_<g>` and `<f>_in_<g>_end` at the start of the code of each inlined
call of a function `g` and after its end, numbered if `g` is inlined several
times into `f`, and notes in the listings with the chain of inlined calls
that each run of instructions belongs to. The layout has 476 such labels.
gcc moves some instructions of an inlined call next to those of others, so
the range of a call can include some instructions of others.

`llvm-symbolizer --dwp` gives the right line numbers for this binary but
attributes instructions to the wrong inlined calls: e.g. code of
`mlk_poly_compress_d5_c` inlined into `mlkem1024_indcpa_enc` comes out as
`mlkem512_keypair_derand`, at a call in `kem.c`. `dwarf_inline.py`
therefore resolves the tree of inlined calls itself, and checks it against
the symbol table: all 60 functions agree.
