# ML-KEM in assembly: the mlkem-native API for AArch64

This directory has an implementation in assembly of the ML-KEM functions
of [mlkem-native](https://github.com/pq-code-package/mlkem-native)'s API,
for all three parameter sets:

    int mlkemL_keypair_derand(uint8_t *pk, uint8_t *sk, const uint8_t *coins)
    int mlkemL_enc_derand(uint8_t *ct, uint8_t *ss, const uint8_t *pk,
                          const uint8_t *coins)
    int mlkemL_dec(uint8_t *ss, const uint8_t *ct, const uint8_t *sk)
    int mlkemL_check_pk(const uint8_t *pk)
    int mlkemL_check_sk(const uint8_t *sk)

for L = 512, 768, 1024, with the same results as mlkem-native's (return
values included). It is written in the style of s2n-bignum, with proofs
in HOL Light of the correctness and the constant-time and memory safety
of all its functions: the new leaves, and those listed under Proofs
below. The randomized `mlkemL_keypair` and `mlkemL_enc` are not here,
since they need a source of randomness: as in mlkem-native, they get 64
or 32 random bytes, call the deterministic function and zero the bytes.

## Structure

The work is in three layers.

 - The leaves, in `../../mlkem`, standalone s2n-bignum-style functions, each
   with its own specification in its header comment:
    - mlkem-native's verified kernels, either as already in s2n-bignum
      (`mlkem_mulcache_compute`, `mlkem_reduce`, `mlkem_tomont`) or as
      `_alt` copies of mlkem-native's current code, which is faster on
      Neoverse-V2 (`mlkem_ntt_alt`, `mlkem_intt_alt`, `mlkem_tobytes_alt`,
      `mlkem_basemul_k{2,3,4}_alt`; mlkem-native has HOL Light proofs of
      these); and s2n-bignum's Keccak-f1600 kernels `sha3_keccak_f1600`
      (x1) and `sha3_keccak4_f1600_alt2` (x4);
    - new ones for what mlkem-native does in C: `mlkem_cbd2`,
      `mlkem_cbd3`, `mlkem_compress_d{4,5,10,11}`,
      `mlkem_decompress_d{4,5,10,11}`, `mlkem_frombytes`,
      `mlkem_frommsg`, `mlkem_tomsg`, `mlkem_check_encoding` (the
      modulus check of an encapsulation key), `mlkem_add_reduce`,
      `mlkem_sub_reduce`, and a faster rejection sampler
      `mlkem_rej_uniform_alt_VARIABLE_TIME` that appends to a partial
      result.
 - The middle layer, here: `mlkem_gen_matrix` (the matrix, with hash jobs
   and noise in the spare lanes of the x4 permutation), `mlkem_getnoise`
   (noise sampling in the x4 lanes), `mlkem_hash_h` and `mlkem_hash_g`
   (SHA3-256 and SHA3-512 with the x1 permutation).
 - The API: `mlkem_kem_template.S`, included by `mlkem512.S`,
   `mlkem768.S` and `mlkem1024.S` after they define the parameter set.
   Besides the API functions it has `mlkemL_pke_encrypt` and
   `mlkemL_pke_decrypt`, shared by encapsulation and decapsulation.

The functions of the upper layers call others (`bl`), so their proofs are
on the linked image of all the functions involved. The tables of
constants (the zetas and the rejection sampling table taken unchanged
from mlkem-native, and the Keccak round constants) are one read-only
block, `mlkem_native2_constants` (`mlkem_native2_constants.S`, with the
layout in `mlkem_native2_consts.h`), whose address the API functions take
with `adrp`/`add`, as `curve25519_x25519base` does for its table, and pass
to the functions below.

## Building

This is the build `asm` of `..` (see `../README.md`). None of these files
is in the `OBJ` list of `../../Makefile`, so they are not in
`libs2nbignum.a`; `proofs.mk` here, generated by
`../../../tools/native_proofs_mk.py` and included by `../../Makefile`, adds
the objects to `MLKEM_NATIVE_OBJ` and the proofs to `MLKEM_NATIVE_PROOFS`
(so they are in `make proofs`), and `image.mk`, written by hand, links the
image of the proofs (see Proofs below). The objects are built by the rule
for `mlkem_native/asm/%.o` of `../../Makefile`, e.g. `make
mlkem_native/asm/mlkem768.o` in `arm`. The
API for one parameter set, `mlkemL.o`, needs `mlkem_gen_matrix.o`,
`mlkem_getnoise.o`, `mlkem_hash_h.o`, `mlkem_hash_g.o` and
`mlkem_native2_constants.o` from here, the new leaves in `../../mlkem` (not
all of them at each level), `mlkem_mulcache_compute`, `mlkem_reduce` and
`mlkem_tomont` in `../../mlkem`, and `sha3_keccak_f1600` and
`sha3_keccak4_f1600_alt2` in `../../sha3`. Every entry point has a BTI
landing pad (`AARCH64_VALID_CALL_TARGET`). The variants of the
directives for Apple platforms are there but have not been tried.

## Proofs

The proofs use the linking approach of the compiled builds of `..` (see
`../README.md`, and `../../../common/relative.ml` for how it works). Each
function of the image that the API reaches has a spec file `X_spec.ml` in
`../../proofs/mlkem_native/asm`, which states its theorems and takes them
as contracts with `assume_spec`, and a proof file `X_proof.ml`, which
proves them relative to the contracts of its callees by loading only their
spec files. `../../proofs/mlkem_native/asm/link.ml`, generated by
`python3 ../../../tools/native_link.py mlkem_native asm` (in `arm`), runs
all the proof files as independent jobs, in parallel with `HOL_PAR=1`, and
closes the contracts, so that the theorems of the API functions have no
assumptions; `proofs.mk` is generated by
`python3 ../../../tools/native_proofs_mk.py mlkem_native asm`.
`make mlkem_native/asm/X_proof.correct` in `arm` runs the proofs of
one function, and `make mlkem_native/asm/link.correct` checks the whole
build.

The proofs are about the image of all the functions: the objects in
`MLKEM_ASM_IMAGE_OBJ` of `image.mk`, linked at address 0 by
`mlkem_native2_image.ld` into `mlkem_native2_image.elf` (`make
mlkem_native/asm/mlkem_native2_image.elf` in `arm`, with GNU ld, or
`aarch64-linux-gnu-ld` when cross-assembling). The rule that links it is
the one part of the make rules that is written by hand, in `image.mk`, as
the generator of `proofs.mk` does not link images.
`../../proofs/mlkem_native/asm/layout.ml` reads the image as one byte list
and installs the names of its symbols as in `../../../common/layout.ml`, so
that a proof refers to the function f or the label f in the image as
`pc + f`. The theorems are thus for this layout of the image, and are
checked again when it changes.

The files, with `X` the name of the function without the parameter set
where there is one, and `k` = 2, 3, 4 for ML-KEM-512, 768, 1024:

- The API: `keypair_derand_kk`, `enc_derand_kk`, `dec_kk`, `check_pk_kk`
  and `check_sk_kk`, and the internal `pke_encrypt_kk` and `pke_decrypt_kk`
  shared by encapsulation and decapsulation. Their theorems have the
  same statements as the proofs of mlkem-native's compiled C: the key
  checks with their constant-time and memory safety, and
  keypair_derand, enc_derand and dec against ML-KEM.KeyGen_internal,
  Encaps_internal (after the modulus check) and Decaps_internal (after
  the hash check), and the internal functions against K-PKE.Encrypt and
  K-PKE.Decrypt, and the constant-time and memory safety of these, with the
  events a function of the addresses and of the public data: rho in key
  generation, ek in encapsulation, and ek and its hash in dk in
  decapsulation. Unlike the compiled builds, the theorems of the API do
  not assume that SampleNTT terminates for the seeds of the matrix: it
  does for every seed of one block of SHAKE128, because Keccak-f1600 is a
  permutation, so the squeezing is periodic and comes back to the padded
  seed, whose last byte makes a 12-bit field < q (`SAMPLE_OK_ALL` of
  `../../../common/fips203/properties/sampling.ml`, with `KECCAK_F1600_INJ`
  of `../../../common/fips202/properties/keccak_permutation.ml`). The tactics
  for them are in `../../proofs/utils/mlkem_native2_api.ml`,
  `mlkem_native2_kem.ml` and `mlkem_native2_kem_safe.ml`, with the lemmas
  on K-PKE of the proofs of mlkem-native's compiled C in
  `mlkem_native2_kpke.ml`.
- `hash_h` (SHA3-256) and `hash_g` (SHA3-512), against `sha3_256` and
  `sha3_512` of `../../../common/fips202/fips202.ml`, with their
  constant-time and memory safety (`mlkem_native2_sponge.ml` for the sponge
  and the use of the permutation); `hash_g` also has its correctness and
  safety in one ("FULL") for messages of less than 72 bytes.
- `gen_matrix_k2`, `gen_matrix_k3` and `gen_matrix_k4`, for the
  configurations that the API uses (key generation, encapsulation and
  decapsulation, with their hash jobs and noise), against
  `mlkem_sample_ntt`, `sha3_256`, `shake256` and the coefficients of
  `mlkem_cbd`, with their constant-time and memory safety in
  `gen_matrix_k2_safe` etc.: the events are a function of the addresses
  and of the public seed rho (and, for decapsulation, whose hash check
  branches on it, the digest H(ek) of the first hash job as a result).
  SampleNTT is the rejection sampling of whole blocks of SHAKE128 output,
  the seeds and the hash jobs are states of lanes, and the sponge works by
  blocks (`mlkem_native2_matrix.ml`, with the lemmas on FIPS 203 of the
  proofs of mlkem-native's compiled C in `mlkem_native_fips203.ml`, and the
  tactics and lemmas that the configurations share, which are the spec and
  proof files `gen_matrix_common` and `gen_matrix_safe_common`, jobs of
  their own).
- `getnoise`, for the configurations of n polynomials that the API uses
  (n = 4, 7, 8, 9 with eta1 = 2, and the first 4 of 4 or 2 of 5 with
  eta1 = 3), against `mlkem_prf` and the coefficients of `mlkem_cbd`, with
  its constant-time and memory safety (`mlkem_native2_noise.ml` for the PRF
  as the state of a lane, the callees, and a simulation driver for code
  whose control flow is fixed by its parameters).
- The kernels of the library that the image links, in `../../mlkem` and
  `../../sha3`, which each have the standalone proof of the library as
  their own proof (`../../proofs/mlkem_ntt_alt.ml` etc.): `ntt_alt`,
  `intt_alt`, `mulcache_compute`, `tomont`, `reduce`, `add_reduce`,
  `sub_reduce`, `tobytes_alt`, `frombytes`, `frommsg`, `tomsg`,
  `basemul_k2_alt`, `basemul_k3_alt`, `basemul_k4_alt`,
  `compress_d4`, `compress_d5`, `compress_d10`, `compress_d11`,
  `decompress_d4`, `decompress_d5`, `decompress_d10`, `decompress_d11`,
  `cbd2`, `cbd3`, `check_encoding`, `rej_uniform_alt_variable_time`,
  `keccak_f1600` (x1) and `keccak4_f1600_alt2` (x4). The standalone
  proofs are unchanged: they are proofs of the library. The spec file of a
  kernel states the contracts that its callers use, which are the
  theorems of the standalone proof and the forms that the callers need
  (the safety with the frame of the correctness theorem, the state of
  the Keccak permutations as 1600-bit words, the coefficients of CBD,
  correctness and events in one theorem for `mlkem_check_encoding`, the
  rejection sampler and the permutations, as the callers' events depend on
  their results), about the code of the standalone proof and not about the
  image; ARM_SUBROUTINE_SIM_TAC uses them for the same code in the image.
  The spec file defines the machine code of the standalone proof from its
  object file and has the definitions that the statements use (copied
  from the standalone proof, which makes them again, which HOL Light
  accepts as a benign redefinition). The proof file `loadt`s the
  standalone proof, so that it runs in the job of the kernel, once, at the
  same time as other jobs, and its theorems that are contracts of the spec
  file are recorded as proofs of them; it then proves the other forms from
  them. A kernel's standalone proof is loaded only by the proof file of the
  kernel, and the proofs of its callers load only its spec file.

The specifications are those of `../../../common/fips202/fips202.ml` and
`../../../common/fips203/fips203.ml`, written by hand from FIPS 202 and FIPS
203, with their properties in the `properties` directories there;
`../../../common/fips203/generated/fips203_equivalence.ml` proves that for
the three parameter sets KeyGen, Encaps, Decaps and the input checks of
the latter are those of a model generated from the pseudocode of FIPS 203
(see `../../../common/fips203/generated/core/README.md`).

### Parallel link: an open issue

With `HOL_PAR=1` and `S2N_PAR_DOMAINS=12`, the job `decompress_d11` fails
with `Failure("EQT_ELIM")` when the other jobs run beside it, whether it is
scheduled first or late (two runs of the whole link, and one with it
first), and the other 59 jobs pass (37 minutes). It passes in all the other
configurations tried: alone on 12 domains with all the files of the link
loaded (only the 59 other jobs missing), in a link of 22 kernels on 10
domains and as a proof file of its own, and, with stock HOL Light, one
proof file after other jobs in one session. The cause is not known; a
global state that the jobs share without `par_local` or `par_counter` (the
counters of `utils/mlkem_native2_noise.ml` and `mlkem_native2_safety.ml`
were such, and are now atomic) is the likely one.

### Theorem names

The theorems of the functions of the build are named as those of the
compiled builds, `MLKEM_NATIVE_<FUNCTION>_K<k>_ASM_IMAGE_SUBROUTINE_CORRECT`
and `..._SAFE`, and `..._FULL` where a function has a theorem of correctness
and safety in one; the contracts of the kernels keep the names of the
theorems of the library (e.g. `MLKEM_NTT_ALT_SUBROUTINE_CORRECT` and
`MLKEM_NTT_ALT_SUBROUTINE_SAFE_FRAMED`). The theorems of the API functions
that `link.ml` closes and prints are the `_SUBROUTINE_CORRECT` and
`_SUBROUTINE_SAFE` theorems of `keypair_derand`, `enc_derand`, `dec`,
`check_pk` and `check_sk`, and, as for the compiled builds, the
`_SUBROUTINE_FIPS203` and `_SUBROUTINE_SAFE_FIPS203` theorems of
`keypair_derand`, `enc_derand` and `dec` of
`../../proofs/mlkem_native/asm/fips203.ml`: there the compiled builds have
their theorems without the hypothesis that SampleNTT terminates, and here
they are the same theorems as `_CORRECT` and `_SAFE`, so that every build
has its final theorems under the same names. Before this build used the
linking approach the theorems were named as follows (the statements are

## Where the speed comes from

About two thirds of mlkem-native's time is in Keccak permutations, and on
Neoverse-V2 the x4 permutation costs 1390 cycles for four states against
668 for one with the x1. mlkem-native runs the long serial hashes H(pk)
and, in decapsulation, J(z || c) on the x1 permutation; here they run in
lanes of the x4 permutation beside the sampling of the matrix, which does
not depend on them. Noise is also sampled in lanes the matrix leaves idle
(for k = 3, and in decapsulation, which decrypts first so that the noise
for the re-encryption can be sampled early). Then the codecs, CBD,
frommsg/tomsg and the key checks, which mlkem-native does in C, are in
Neon assembly, 2-9 times faster each, and the rejection sampler is 1.7
times faster. The arithmetic kernels are mlkem-native's.

Key generation gains least: its H(pk) is a serial tail with nothing to
run beside it, and its Keccak schedule is otherwise already optimal; the
x1 permutation is at the throughput bound of the four integer pipelines,
and the SHA3 instructions issue only one per cycle on this core.

Stack use, in bytes (keypair_derand, enc_derand, dec): 9200, 8640, 10304
for ML-KEM-512; 13552, 13504, 15824 for ML-KEM-768; 20656, 19392, 22656
for ML-KEM-1024. The stack buffers holding secrets are zeroed before
returning.

## Constant time

Everything is constant-time in the secret data. The rejection sampling of
the matrix, and the scheduling around it, depend only on the public seed
rho; in key generation rho is computed from the secret d, and the build
for testing with valgrind (`MLKEM_CT_TESTING` defined when preprocessing
the per-level files) marks it public there with memcheck's client
request, as mlkem-native does with `MLK_CONFIG_CT_TESTING_ENABLED`. The
results of the key checks are public.

## Testing

The tests and benchmarks are in `../../../tests/mlkem_native2` (see its
README). They compare
these functions with mlkem-native's portable C on random and edge-case
inputs, including the rare paths (implicit rejection, invalid keys, the
fourth block of rejection sampling), check the KAT hashes and the ACVP
and Wycheproof vectors, run under memcheck with exact-size buffers and
for constant time with the secrets undefined, check the ABI
(callee-saved registers, x18, sp) and that no secret is left on the
stack, and call the functions through pointers with BTI enforced.
