# FIPS 203: the generated model equals the handwritten model (HOL Light)

This directory proves, in HOL Light, that the FIPS 203 (ML-KEM) model
generated by the FIPS pseudocode compiler
(`common/fips203/generated/fips203_generated.ml`) computes the same results
as the handwritten model (`common/fips203/fips203.ml`, with
`common/fips202/fips202.ml` for SHA-3), for ML-KEM-512, -768 and -1024.

## What is claimed

For inputs of the right length, each generated ML-KEM function returns the
result that the corresponding handwritten function computes. **The statements
are in [`fips203_equivalence.ml`](../fips203_equivalence.ml)**; everything
else is in this directory (the proofs, the lemma interface that connects
them, and the tools). The properties of the handwritten model that the proofs
use are in `common/fips202/properties/` and `common/fips203/properties/`.
Here are the statements for ML-KEM-512; the other two parameter sets (`768`,
`1024`) have the same shape, with the sizes of FIPS 203 Table 2.

**KeyGen.** The generated `ML_KEM_KeyGen_MLKEM512_Configuration_hol` takes no
seeds as arguments. It asks an entropy oracle `ent` for random bytes: `ent 0`
is the first request, `ent 1` the second. If the oracle returns `d` and `z`,
the result is what the handwritten `mlkem_keygen_internal` (FIPS 203
Algorithm 16) computes from `d` and `z`. KeyGen runs no input check, so
there is no `_checked` variant. `mlkem512` is the parameter set
`(k, eta1, eta2, du, dv) = (2, 3, 2, 10, 4)`:

    !ent d z. ent 0 = SOME d /\ ent 1 = SOME z
              ==> ML_KEM_KeyGen_MLKEM512_Configuration_hol ent =
                  Value (Native_Value (mlkem_keygen_internal mlkem512 d z))

`Value x` is how every generated function reports success, and
`Native_Value x` wraps a produced result.

**Encaps.** Likewise, with the message `m` from the oracle. The handwritten
`mlkem_encaps_checked` is `mlkem_encaps_internal` (FIPS 203 Algorithm 17)
preceded by the encapsulation key check of section 7.2: if `ek` passes the
check, the result is `SOME kc` (with `kc` the pair of shared key and
ciphertext), otherwise `NONE`. The generated `Encaps` does not run that
check; the generated model has it as a separate function (see below). The
statements therefore compose the two. When the generated check passes, the
generated `Encaps` returns `kc` exactly when `mlkem_encaps_checked` returns
`SOME kc`; when the generated check fails, `mlkem_encaps_checked` returns
`NONE`:

    !ent ek m kc.
      ent 0 = SOME m /\ LENGTH m = 32 /\
      ML_KEM_EncapsKeyCheck_MLKEM512_Configuration_hol ek = Value T
      ==> (ML_KEM_Encaps_MLKEM512_Configuration_hol ent ek =
           Value (Native_Value kc) <=>
           mlkem_encaps_checked mlkem512 ek m = SOME kc)

    !ek m. ML_KEM_EncapsKeyCheck_MLKEM512_Configuration_hol ek = Value F
           ==> mlkem_encaps_checked mlkem512 ek m = NONE

**Decaps.** In the same way, with `mlkem_decaps_checked`
(`mlkem_decaps_internal`, Algorithm 18, preceded by the check of section 7.3)
and the shared key `kk`:

    !dk c kk.
      ML_KEM_DecapsInputCheck_MLKEM512_Configuration_hol dk c = Value T
      ==> (ML_KEM_Decaps_MLKEM512_Configuration_hol dk c = Value kk <=>
           mlkem_decaps_checked mlkem512 dk c = SOME kk)

    !dk c. ML_KEM_DecapsInputCheck_MLKEM512_Configuration_hol dk c = Value F
           ==> mlkem_decaps_checked mlkem512 dk c = NONE

**The checks themselves.** The generated `Encaps` and `Decaps` do not run the
checks of sections 7.2 and 7.3; the generated model has them as separate
functions. They agree with the handwritten ones:

    !ek. ML_KEM_EncapsKeyCheck_MLKEM512_Configuration_hol ek =
         Value (mlkem_ek_check mlkem512 ek)

    !dk c. ML_KEM_DecapsInputCheck_MLKEM512_Configuration_hol dk c =
           Value (mlkem_decaps_check mlkem512 dk c)

**The internal algorithms** (FIPS 203 Algorithms 16 to 18), which take their
random inputs as arguments, are related in the same way, for example
`MLKEM_KEYGEN_INTERNAL_512_FINAL`:

    !d z. ML_KEM_KeyGen_internal_MLKEM512_Configuration_hol d z =
          Value (mlkem_keygen_internal mlkem512 d z)

The names of all of these are `MLKEM_KEYGEN_<n>_FINAL`,
`MLKEM_{ENCAPS,DECAPS}_<n>_{AGREE,REJECT}`,
`MLKEM_{KEYGEN,ENCAPS,DECAPS}_INTERNAL_<n>_FINAL`, `MLKEM_EK_CHECK_<n>_EQUIV`
and `MLKEM_DECAPS_CHECK_<n>_EQUIV`, for `<n>` in 512, 768, 1024. Everything
in this directory is proof infrastructure.

## What is not claimed

* Inputs of the wrong length. The generated functions fault on them; the
  handwritten ones are unspecified there.
* What the generated Encaps and Decaps return when their input check fails.
  The generated functions do not run the check, and the statements say only
  that the handwritten functions return `NONE` then. (The internal forms hold
  for every input of the right length, checked or not.)
* What the generated KeyGen and Encaps do when the random generator fails.
  That is behaviour of the generated model only; the handwritten model has no
  such case, and there is nothing to compare.
* That `common/fips203/fips203.ml` matches the FIPS 203 text, or that the compiler is
  correct. This work only relates the two models to each other.
* SHA-3. Both models use the same SHA-3 constants (the generated files bind
  their hash functions to `sha3_*` and `shake*` from
  `common/fips202/fips202.ml`; see `base.ml`). SHA-3 is not checked against
  FIPS 202 or test vectors here.

## How to check

    common/fips203/generated/core/tools/check-all.sh [logfile]

It needs HOL Light: either set `HOL_SH` to a `hol.sh`, or have the nix
`hol_light` shell of an mlkem-native checkout at `$MLKEM_NATIVE` (default
`~/repos/mlkem-native`). The proofs were run with the nix HOL Light snapshot
of 2026-05-19 (OCaml 5.4.1); they have not been run with the HOL Light
revision that s2n-bignum's CI pins. One run took about 520 s (most of it
loading the two models) in one process; memory use was not measured.

The script loads `all.ml` in a fresh session, checks that each interface
lemma is a hypothesis-free theorem with exactly the stated conclusion, and
prints `FIPS203-EQUIV-CHECK-PASSED <n> lemmas`. It also writes
`<logfile>.manifest` with the hashes of every file it loaded. A normal log
has 25 "Benign redefinition" warnings (the definitions of `fips202.ml` loaded
a second time, see `base.ml`) and many "inventing type variables" warnings,
which are not errors.

## How the two models relate

The handwritten model works in R_q with plain functions and lists of bytes.
The generated model follows the FIPS pseudocode step by step: results are
`Value x`, `Fault e` or `Nontermination`, sequenced by `native_bind`; loops
are folds over a schedule of integer indices; polynomials, vectors and
matrices are records over lists of Z_q residues (`FIPS203_Zq (Residue n)`);
every arithmetic step reduces modulo q. `base.ml` defines the maps between
the two representations (`zpoly`, `zvec`, `zmat`, `zqlist`) used in the
intermediate lemmas.

## Termination of ML-KEM

Following Barbosa and Schwabe, "Kyber terminates" (ePrint 2023/708),
`common/fips203/properties/sampling.ml` shows that the rejection sampling of
the handwritten model always terminates: for every 34-byte input (`rho`
followed by two index bytes) the SHAKE128 stream contains the 256 values
below q that `SampleNTT` needs. The equivalence statements need this, because
the generated `SampleNTT` loops until it has them. The padded input is one
168-byte block `B`. Keccak-f is a permutation, so `B` lies on the cycle of
the squeeze states; bytes 35 to 166 of `B` are zero, so every pass over the
cycle contributes 12-bit fields equal to 0, which are below q. The paper
takes "Keccak-f is a permutation" as known; here it is proved, in
`common/fips202/properties/keccak_theta_injective.ml` (theta is injective by
six squarings of its linear map in characteristic 2) and
`common/fips202/properties/keccak_permutation.ml` (the other four steps and
the composition).
