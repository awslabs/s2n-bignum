# Compiled code from mldsa-native

This directory contains x86-64 code compiled from the portable C
implementation in [mldsa-native][1], transcribed from the x86-64 binaries
in its `binary` branch, and the scripts that produce and check
the files the proofs in `../proofs/mldsa_native` use. As for the AArch64
code of mldsa-native in `../../arm/mldsa_native`, the aim is to verify
compiler-generated rather than hand-written code; the code here is only
used for the proofs and is not part of the library.

[1]: https://github.com/pq-code-package/mldsa-native

The proofs are proved function by function against a functional
specification that follows the C code: `../../common/mldsa_native_*.ml`
defines, for each C function, the HOL function on machine words that it
computes. These are the same specifications as for the AArch64 code, since
the C code is the same. Relating them to FIPS 204 is a separate step that
does not involve the compiled code (see "Relation to FIPS 204" below).

## Organization

The files for each build of the binary are in directories named after the
compiler and the optimization level, `<build>` = `<compiler>_<level>`,
e.g. `gcc12_O2` for the gcc 12 `-O2` binary, followed by the configuration
if it is not the default one: `gcc12_O2_reduced_ram` is the gcc 12 `-O2`
binary built with `MLD_CONFIG_REDUCE_RAM` (see its `README.md`). For a
build:

 - `<build>/libmldsa.S` is the transcription of the whole image of the
   binary, generated by `gen_libmldsa_s.py`;
 - `../proofs/mldsa_native/<build>/layout.ml`, generated by
   `gen_layout.py`, gives names to the addresses in the binary;
 - `../proofs/mldsa_native/<build>/libmldsa.ml` defines the image;
 - `../proofs/mldsa_native/<build>/<f>_spec.ml` states the theorems for
   the function `<f>` (assumed with `assume_spec`, see
   `../../common/relative.ml`) and `<f>_proof.ml` proves them,
   relative to the statements of its callees;
 - `../proofs/mldsa_native/<build>/fips204.ml`, `fips204_sign.ml` and
   `fips204_verify.ml` restate the CORRECT theorems of the API functions
   with the FIPS 204 specification `../../common/fips204/fips204.ml`, and
   `fips204_safe.ml` states their SAFE theorems without the hypotheses
   that the samplers terminate (see below);
 - `<build>/proofs.mk`, generated by `../../tools/native_proofs_mk.py
   mldsa_native <build>` from the
   `needs` of the proofs, lists the transcriptions and proofs for
   `../Makefile`, which includes it.

`../../tools/native_link.py mldsa_native <build>` generates the link file
of a build,
`../proofs/mldsa_native/<build>/link.ml`, which loads all proof files
and then the FIPS 204 files in one session and discharges the assumed
statements of the callees.

Functions whose code is the same for all parameter sets, such as
`mldsa_poly_add`, have files named after the function without the
namespace (`poly_add_spec.ml`), and those of one parameter set have the
suffix `_44`, `_65` or `_87`.

The scripts are x86-64 versions of those in `../../arm/mldsa_native`.
`gen_layout.py` gives the same names as the AArch64 one wherever the code
has the same shape, and also names the jump tables of `switch`
statements, which gcc uses on x86-64 but not on AArch64.
`../proofs/mlkem_native/relative.ml` loads the x86 base and
`../../common/relative.ml`, which makes the proofs relative to the
statements of the callees, as for AArch64. The lemmas and tools that do
not depend on the instruction set are in
`../../common/fips204/properties/mldsa_native*.ml`, shared with the
AArch64 proofs; `../proofs/utils/mldsa_native*.ml` has the x86 parts.

## Source of the code

The code is transcribed from the x86-64 binaries in the `binary` branch of
mldsa-native, at commit `01be6a9` ("binaries: Rebuild x86-64 ML-DSA
without stack protection"), which replaced the AArch64 binaries at the same
paths by x86-64 ones (the AArch64 binaries are at commit `65f9995`). As
recorded in `binaries/builds.json` there, `scripts/build-binaries` built
them from mldsa-native commit `d38418ea3d4c`, in the nix shell `.#gcc12`
(gcc 12.3.0 and binutils 2.41) on an x86-64 Linux machine, with the flags
`-g -gdwarf-4 -gsplit-dwarf -fPIC -fno-stack-protector` and the
optimization level `-O2`, and, for the reduced-RAM configuration,
`-DMLD_CONFIG_REDUCE_RAM` in addition. The "multilevel" build
(`examples/multilevel_build`) was linked with
`ld -shared -Bsymbolic -soname libmldsa.so --whole-archive`, using the
version script `binaries/libmldsa.map`, to give `libmldsa.so`. In this
build the code shared by the three parameter sets is compiled once, with
the namespace `mldsa_`, and the rest once per parameter set, with the
namespaces `mldsa44_`, `mldsa65_` and `mldsa87_`. The binary has the same
192 functions, with the same names, as the AArch64 binary of the same
build.

| File (gcc 12.3.0)                          | Binary in the `binary` branch               |
|--------------------------------------------|---------------------------------------------|
| gcc12_O2/libmldsa.S                        | binaries/multilevel/gcc12/O2/libmldsa.so    |
| gcc12_O2/keccakf1600_permute.S             | binaries/multilevel/gcc12/O2/libmldsa.so    |
| gcc12_O2_reduced_ram/libmldsa.S            | binaries/reduced-ram/multilevel/gcc12/O2/libmldsa.so |
| gcc12_O2_reduced_ram/keccakf1600_permute.S | binaries/reduced-ram/multilevel/gcc12/O2/libmldsa.so |

The reduced-RAM build is compiled with `-DMLD_CONFIG_REDUCE_RAM`; see
`gcc12_O2_reduced_ram/README.md` for its hash and how it differs.

`gcc12_O2/keccakf1600_permute.S` is the code of `mldsa_keccakf1600_permute`
alone, with its table of round constants as a separate symbol. Its code is
that of `mlkem_keccakf1600_permute` in the x86-64 gcc 12 -O2 build of
mlkem-native, apart from the displacements of the table, and so its proof
is that of the x86-64 mlkem-native proofs, on the separate object,
transferred to the image (as for AArch64). `check_transcription.py`, also
from the x86-64 mlkem-native proofs, checks the separate object against
the binary:

```
python3 mldsa_native/check_transcription.py \
  mldsa_native/gcc12_O2/keccakf1600_permute.o \
  mldsa_native_keccakf1600_permute_gcc12_O2 \
  <build>/multilevel/gcc12/O2/libmldsa.so \
  mldsa_keccakf1600_permute \
  mld_KeccakF_RoundConstants mld_KeccakF_RoundConstants
```

The SHA-256 hash of the binary used, which is that in
`binaries/SHA256SUMS` of commit `01be6a9`, is:

```
multilevel/gcc12/O2/libmldsa.so
  60e02b1c1efa208bd35d21fc6e46faf798c1e1a311ace8c96551a9ae6515281d
```

The image starts at address 0, so it includes the dynamic string table,
where the linker records the directory of the build as `RUNPATH`
(`/tmp/native-x86-no-stack-protector.16lXCUsN/mldsa-source/outputs/out/lib`);
the split debug information records the paths of its files. A binary built
from the same source in another directory therefore differs from this one
there, but its code and read-only data are the same.

Unlike the AArch64 binaries, this one is built without gcc's stack
protector, which the nix shell otherwise enables (the x86-64 binaries first
committed to the branch, built from the same source, imported
`__stack_chk_fail`, and `01be6a9` rebuilt them for this reason). On x86-64 Linux the stack
protector reads its guard at offset 0x28 from the base of the FS segment,
in thread-local storage, rather than through the global offset table as on
AArch64, and the x86 model has no segment bases. With the stack
protector, 61 of the 192 functions, including 36 of the 42 API functions,
would copy the guard to the stack and check it before returning.

To regenerate the files of the build, in the `x86` directory, with
`<build>` the `binaries` directory of a checkout of mldsa-native at
commit `01be6a9` of the `binary` branch (the same holds for the commands
above):

```
python3 mldsa_native/gen_libmldsa_s.py \
  <build>/multilevel/gcc12/O2/libmldsa.so \
  mldsa_native_libmldsa_gcc12_O2 "gcc 12, -O2" \
  multilevel/gcc12/O2/libmldsa.so $PWD/../include \
  > mldsa_native/gcc12_O2/libmldsa.S
python3 mldsa_native/gen_layout.py \
  --name multilevel/gcc12/O2/libmldsa.so \
  <build>/multilevel/gcc12/O2/libmldsa.so \
  > proofs/mldsa_native/gcc12_O2/layout.ml
python3 ../tools/native_proofs_mk.py mldsa_native gcc12_O2 \
  > mldsa_native/gcc12_O2/proofs.mk
python3 ../tools/native_link.py mldsa_native gcc12_O2 \
  > proofs/mldsa_native/gcc12_O2/link.ml
```

`gen_libmldsa_s.py` assembles the transcription as the `Makefile` does
(it calls `as`, which must be an x86-64 assembler: on another host, put a
cross-assembler first in the `PATH`, and give the `Makefile` its name as
`ASSEMBLE`) and checks that it is byte-for-byte the image of the binary,
from address 0 to the end of the read-only data, writing any instruction
that the assembler would encode differently, the NOPs and the
instructions that refer to the global offset table, which is outside the
image, as `.byte`.
`libmldsa.ml` checks that the image has the size given in the layout file.

## The compiled code

Unlike the hand-written x86 code in `..`, the compiled code uses the
legacy SSE2 forms of vector instructions rather than the AVX2 ones, 8-bit
and 16-bit forms of scalar instructions, and the quadword string
operations `rep stos` and `rep movs`, which gcc uses to zero and copy
blocks of fixed size, all of which are in the x86 model in `../proofs`.
The aligned SSE loads and stores fault if the address of their operand is
not a multiple of 16, so the polynomials that the vectorized loops read
and write must be aligned, as they are in mldsa-native, whose polynomials
are aligned to 32 bytes.

The compiled code also uses the "red zone", the 128 bytes below the stack
pointer, which the System V ABI allows a function to use for data that is
not needed across calls, without moving the stack pointer, and calls the C
library through the procedure linkage table, whose entries jump to the
addresses in the global offset table. In each of the three
`prepare_domain_separation_prefix` functions, gcc compiles the `switch`
on the hash function to an indirect jump through a table of offsets in
the read-only data. The packing functions `mld_polyeta_pack`,
`mld_polyz_pack` and `mld_polyt0_pack` write to the stack below their
frames: mldsa-native zeroizes their temporary arrays (commit `ea97cc798`,
"poly: Zeroize intermediate buffers of the packing functions"), which gcc
compiles to stores of zeros to the stack, in the red zone, with no call of
`memset`; the frames in their statements include these stores.

## What is proved

For each of the 192 functions of the image, `<f>_proof.ml` proves three
theorems about its code, as for the AArch64 code of mldsa-native:

 - `..._FULL`: `?f_events. !e args. H ==> ensures x86 (P /\ events = e)
   (Q /\ ?e2. events = APPEND e2 e /\ e2 = f_events <public args> /\
   memaccess_inbounds e2 R W) C`. This combines three properties.
   Correctness: the postcondition Q, with the functional specifications
   of `common/mldsa_native_*.ml`. Constant time: the trace of memory
   addresses and branch targets of the execution is a fixed function
   f_events of the public arguments only. Memory safety: all loads are
   within the regions R and all stores within W.
 - `..._CORRECT`: `!args. H ==> ensures x86 P Q C`, derived from FULL.
 - `..._SAFE`: FULL without Q, in the form of s2n-bignum's other safety
   theorems, derived from FULL.

FULL is the primary theorem because the callers that branch on the
results of their callees need both the values and the events of their
callees at once. These are signing, verification and the samplers.

The statements follow the AArch64 ones for the same functions, adapted
to the x86-64 calling convention of the System V ABI: on entry the
return address is at the stack pointer and the arguments after the sixth
are above it, and the function returns to that address with RSP 8 above
its value on entry. The function and its callees may write the N bytes
below the return address, `bytes(word_sub stackpointer (word N),N)`,
where N is the greatest depth below it that the code of the function and
its callees accesses, including the red zone.

`link.ml`, generated by `native_link.py`, loads all the proofs and the FIPS
204 files (see below) in one session and closes the theorems of the API
functions and of the FIPS 204 files, so that they have no assumptions. In
`..`, `make mldsa_native/<build>/link.correct` checks a build. It runs the
proof files as independent jobs, one after the other by default, or at the
same time on `S2N_PAR_DOMAINS` domains when built with `HOL_PAR=1`, the
costliest first, as given by `link_costs.tsv` of the build, which `python3
../tools/link_costs.py mldsa_native <build> [LOG]` updates (see "Running
proofs in parallel" in `../../README.md`, which also gives the reference
configuration and the run times).

### The public arguments of the events

As for AArch64, besides addresses, lengths (of messages and contexts),
pc and the return address, the events may depend on exactly what the C
code declassifies (`MLD_CT_TESTING_DECLASSIFY`) or treats as public.
These are given as named HOL functions of the inputs:

 - the matrix A and anything derived from rho (rej_uniform,
   poly_uniform, poly_uniform_4x, polyvec_matrix_expand_eager,
   pk_from_sk's rho);
 - which nibbles the eta samplers accept (`mld_rej_eta_declass`,
   `mld_poly_uniform_eta_declass`, `mld_keypair_declass`);
 - the challenge seed c~ (poly_challenge and, per attempt, signing);
 - per signing attempt, the result of each norm check up to the first
   that fails and, if all pass, w0 - c s2 + c t0 and w1 packed
   (`mld_sign_attempt_declass`); also the number of attempts and the
   signature;
 - for verification, all its inputs (pk, the signature, the message);
 - for pk_from_sk, rho and the result of the check of the key.

## Trusted base

The theorems depend on the following, which the proofs do not establish.
`../../SOUNDNESS.md` discusses the gaps of s2n-bignum's proofs in general.

 - HOL Light's kernel and the OCaml that runs it. Every proof run ends with
   HOL Light's `check_axioms ()` (called by `../../tools/build-proof.sh`),
   which fails if the session has an axiom besides HOL Light's own three.
   `../../common/relative.ml` forms the theorems of a link file with kernel
   rules: `assume_spec` uses `ASSUME`, and `relative_close` discharges each
   assumption with `PROVE_HYP` and fails if one is left. With `HOL_PAR=1`,
   the kernel must also be sound when called from several domains (see
   "Running proofs in parallel" in `../../README.md`).
 - The model of x86-64: `../proofs/x86.ml`, `../proofs/instruction.ml` and
   `../proofs/decode.ml`, which give the semantics
   of the instructions and decode machine code to instructions, and, for
   the theorems of constant time and memory safety, the events that the
   semantics emits (`../../common/safety.ml`). The model is tested, not
   proved, against other implementations of the instructions (see B1 in
   `../../SOUNDNESS.md`).
 - That the machine code proved is the machine code of the binary. The
   proofs are about the code in `<build>/libmldsa.S` and in
   `<build>/keccakf1600_permute.S`, as assembled into the `.o` files by
   `../Makefile`. `gen_libmldsa_s.py` checks that the assembled whole-image
   transcription is byte for byte the image of `libmldsa.so` when it writes
   it, and `check_transcription.py` compares `keccakf1600_permute.o` with
   the binary; the second is run by hand, and neither `make` nor CI runs
   either. The binaries are those of the `binary` branch of mldsa-native, at
   the commit given in "Source of the code" (and, for the reduced-RAM
   build, in `gcc12_O2_reduced_ram/README.md`), which also give their
   SHA-256 hashes.
 - The specifications. The theorems about the code (`..._FULL`, `..._CORRECT`
   and `..._SAFE`) state results with the functional specification of each
   C function in `../../common/mldsa_native_*.ml`. The `..._FIPS204`
   theorems state the results of the API functions with FIPS 204 in
   `../../common/fips204/fips204.ml` and FIPS 202 in
   `../../common/fips202/fips202.ml`, which are written by hand (see
   "Relation to FIPS 204" for their hypotheses). A second model of
   FIPS 204, compiled from the pseudocode of the standard, is proved equal
   to `fips204.ml` for key generation, signing and verification, with and
   without pre-hashing, for ML-DSA-44, -65 and -87
   (`../../common/fips204/generated/core/README.md`), so an error in the
   specification would have to be in both. That README says what is not
   covered: neither model is checked against the text of FIPS 204, and the
   statements assume that the random generator does not fail and that
   messages are whole bytes (except the pre-hash of HashML-DSA).
 - Which values the events of a call may depend on: those listed under "The
   public arguments of the events". A reader has to agree that they are
   public.
 - The behaviour of the C library functions and of randombytes, whose code
   is not in the image: the contracts under "Hypotheses".

## Hypotheses

The theorems for the API functions (the `..._FULL`, `..._CORRECT` and
`..._SAFE` theorems of the link file) have these hypotheses; the link file
discharges all others.

 - The image is loaded at a 4096-aligned pc and fits in the address space.
 - The written regions are disjoint from each other, from the inputs, from
   the image and from the return address on the stack.
 - No alignment of the stack pointer is assumed. 54 functions, whose
   local arrays mldsa-native aligns, align it to 32 bytes with
   `and rsp, -32`: the API functions other than verify_extmu and
   prepare_domain_separation_prefix, compute_pack_t0_t1 and the samplers
   that keep a Keccak state on the stack. For these N includes the up to
   31 bytes by which this lowers the stack pointer, and the proofs use
   `../proofs/utils/mldsa_native_realign.ml`. The five functions that
   use aligned SSE loads and stores on the polynomials that they are
   given (poly_add, poly_sub, poly_shiftl, poly_reduce and
   poly_power2round) assume them 16-aligned. Seven more functions
   assume that the stack pointer is aligned as the ABI requires on entry,
   `aligned 16 (word_add stackpointer (word 8))`: `mldsa_polyt0_pack` and
   `mldsa{44,65,87}_polyz_pack`, which clear their temporary array
   (mldsa-native zeroizes it) with aligned SSE stores to the stack, and
   `mldsa{44,65,87}_pack_sig_z`, which tail-calls the latter. Their callers
   have realigned the stack, so the theorems of the API functions do not
   assume it.
 - The direction flag is clear on entry, as the ABI requires, for the 83
   functions whose code, or that of their callees, uses `rep stos` or
   `rep movs` or calls the C library.
 - Each theorem assumes the contracts of the C library functions that its
   function or the functions it calls use. memset, memcpy and randombytes
   satisfy the contracts of `../proofs/utils/mldsa_native_libc.ml` through
   their GOT entries: `memset_full_contract` (or `memset_ret_full_contract`),
   `memcpy_full_contract` and `randombytes_safety_contract`. Each is a
   contract for correctness and for constant time and memory safety
   together. A contract is about the function at the address that the PLT
   stub reads from the GOT, and holds in every state in which the region
   (ea,el) holds `ev`, the direction flag is clear and the return address is
   at the stack pointer. The functions are in that one region, which holds
   their code and data and which the caller does not write. They return to
   the return address with RSP 8 above, and change only the registers that
   the ABI allows and the output buffer, and no other memory. So they use no
   stack except to read their return address. memset sets the `len` bytes
   at `dst` to the low byte of `c`; `memset_ret_full_contract` also returns
   `dst` in RAX, as the C standard says, which `mld_sig_unpack_hints` uses.
   memcpy copies `len` bytes from `src` to `dst`; the two buffers do not
   overlap. randombytes writes `len` bytes at `buf`, and neither the bytes
   nor the value that it returns are constrained: it may return any bytes,
   or fail (the code then returns `MLD_ERR_RNG_FAIL`, which the model has no
   counterpart for). The events of a call are a function of its arguments,
   the stack pointer and the return address, and the call reads only its
   argument buffers, its return address and the region (ea,el) and writes
   only its output buffer.
 - Termination of the rejection samplers and of SampleInBall is not
   assumed by the FIPS 204 theorems (`mldsa_native_fips204_*` and
   `gcc12_O2/fips204*.ml`):
   `../../common/fips204/properties/mldsa_native_fips204_terminates.ml`
   proves the predicates `mld_matrix_terminates`,
   `mld_keypair_terminates_XX`, `mld_poly_challenge_terminates` and
   `mld_sign_terminates_XX` from the fact that Keccak-f[1600] is a
   permutation (`../../common/fips204/properties/terminates.ml`). The
   contracts of the C functions themselves (the `_spec.ml` files) still take
   them as preconditions, and so does `mld_rej_uniform_terminates` of
   `mld_poly_uniform`; `MLD_FIPS204_DISCHARGE` removes them when a
   FIPS 204 theorem uses such a contract. For the SAFE theorems of the
   API functions, `<build>/fips204_safe.ml` does the same: each
   `..._SAFE_FIPS204` is a SAFE theorem with them discharged, as each
   `..._SAFE_FIPS203` of mlkem-native is.
 - Signing makes at most maxatt = (65535 - l) DIV l attempts (16382,
   13106 and 9361), and otherwise returns
   `MLD_ERR_SIGN_ATTEMPTS_EXHAUSTED`.

## Relation to FIPS 204

`../../common/fips204/fips204.ml` is a mathematical specification of
ML-DSA (FIPS 204), and `../../common/fips204/properties/fips204_properties.ml`
proves its properties.
Among them is the equivalence with the alternative way of checking the
low bits and computing the hints of Section 5.1 of the Round 3
Dilithium specification, which FIPS 204 permits and mldsa-native uses
(`MLDSA_SIGN_MU_ALT`). The lemmas of
`../../common/fips204/properties/mldsa_native_fips204_*.ml`, shared with
the AArch64 proofs, relate the specification of the C code to FIPS 204,
with no machine code involved:

 - `_ntt`: the NTT, its inverse and the Montgomery products as
   operations of R_q;
 - `_sample`: SHAKE, ExpandA, RejBoundedPoly, ExpandMask and
   SampleInBall;
 - `_round`: reduce32, Power2Round, Decompose, UseHint, the hints and
   the norm checks;
 - `_pack`: the bit packings, HintBitPack and HintBitUnpack;
 - `_keypair`: the keys of key generation are those of
   `mldsa_keygen_internal` (`MLD_FIPS204_KEYPAIR_44` etc.);
 - `_pk_from_sk`: the public key computed from a secret key is
   pkEncode(rho, t1) for skDecode(sk). The check passes iff s1 and s2
   are within [-eta,eta], t0 matches and tr = H(pk). In particular,
   pk_from_sk accepts the secret key that key generation makes and
   recovers its public key (`MLD_FIPS204_PK_FROM_SK_KEYGEN_44` etc.);
 - `_sign`: signing is FIPS 204 signing (`MLD_FIPS204_SIGN_44` etc.);
 - `_verify`: verification is FIPS 204 verification
   (`MLD_FIPS204_VERIFY_44` etc.).

`../proofs/mldsa_native/gcc12_O2/fips204.ml`,
`fips204_sign.ml` and `fips204_verify.ml` derive the theorems for the
API functions from the lemmas and the CORRECT theorems. For each API
function and parameter set, a theorem `..._FIPS204` states the function
with the FIPS 204 functions, with its inputs and outputs as byte
strings: `mldsa_keygen_internal` and `mldsa_keygen` for key generation,
`mldsa_sign_internal`, `mldsa_sign_mu`, `mldsa_sign` and
`hash_mldsa_sign` for signing, and `mldsa_verify_internal`,
`mldsa_verify_mu`, `mldsa_verify` and `hash_mldsa_verify` for
verification. They have two further hypotheses:

 - Signing equals FIPS 204 signing when the fields of s2 in the secret
   key are at most 2 * eta. This holds for every key made by key
   generation. For a malformed key, FIPS 204 can accept an attempt that
   the code rejects (mldsa-native does not check the key when signing).
 - The result of the code is the outcome of the FIPS 204 function, with
   the return codes of `mldsa_native.h` for its cases
   (`common/mldsa_native_errors.ml`). Signing returns an
   `mldsa_sign_result` (`MLDSA_Sign_Success`, `MLDSA_Sign_Error_BadContext`
   for a context of more than 255 bytes, and
   `MLDSA_Sign_Error_OutOfAttempts`) and verification an
   `mldsa_verify_result` (`MLDSA_Verify_Success`,
   `MLDSA_Verify_Error_InvalidSignature` and
   `MLDSA_Verify_Error_BadContext`). `mld_sign_status` and
   `mld_verify_status` map them to `MLD_OK`, `MLD_ERR_INVALID_ARG`,
   `MLD_ERR_SIGN_ATTEMPTS_EXHAUSTED` and `MLD_ERR_INVALID_SIGNATURE`.
   As the code makes at most maxatt attempts, the theorems for signing
   pass the bound `SOME maxatt` to the signing functions, which then make
   the same number of attempts; with `NONE` they search without limit, as
   FIPS 204 does. `MLD_ERR_RNG_FAIL`, when the random generator fails,
   has no counterpart in the model, which has the randomness as an
   argument.
