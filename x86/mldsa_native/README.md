# Compiled code from mldsa-native

This directory contains x86-64 code compiled from the portable C
implementation in [mldsa-native][1], transcribed from a binary built in the
same way as its pre-built binaries, and the scripts that produce and check
the files the proofs in `../proofs/mldsa_native` use. As for the AArch64
code of mldsa-native in `../../arm/mldsa_native`, the aim is to verify
compiler-generated rather than hand-written code; the code here is only
used for the proofs and is not part of the library.

[1]: https://github.com/pq-code-package/mldsa-native

The proofs are proved function by function against a functional
specification that follows the C code: `../../common/mldsa_native_*.ml`
defines, for each C function, the HOL function on machine words that it
computes. These are the same specifications as for the AArch64 code, since
the C code is the same. Relating them to FIPS 204 is a separate step that
does not involve the compiled code (see "Relation to FIPS 204" below).

## Organization

The files for each build of the binary are in directories named after the
compiler and the optimization level, `<build>` = `<compiler>_<level>`,
e.g. `gcc12_O2` for the gcc 12 `-O2` binary. For a build:

 - `<build>/libmldsa.S` is the transcription of the whole image of the
   binary, generated by `gen_libmldsa_s.py`;
 - `../proofs/mldsa_native/<build>/layout.ml`, generated by
   `gen_layout.py`, gives names to the addresses in the binary;
 - `../proofs/mldsa_native/<build>/libmldsa.ml` defines the image;
 - `../proofs/mldsa_native/<build>/<f>_spec.ml` states the theorems for
   the function `<f>` (assumed with `assume_spec`, see
   `../proofs/mldsa_native/relative.ml`) and `<f>_proof.ml` proves them,
   relative to the statements of its callees;
 - `../proofs/mldsa_native/<build>/fips204.ml` and `fips204_*.ml` restate
   the CORRECT theorems of the API functions with the FIPS 204
   specification `../../common/fips204.ml`;
 - `<build>/proofs.mk`, generated by `gen_proofs_mk.py <build>` from the
   `needs` of the proofs, lists the transcriptions and proofs for
   `../Makefile`, which includes it.

`gen_link.py <build>` generates the link file of a build,
`../proofs/mldsa_native/<build>/link.ml`, which loads all proof files
and then the FIPS 204 files in one session and discharges the assumed
statements of the callees.

Functions whose code is the same for all parameter sets, such as
`mldsa_poly_add`, have files named after the function without the
namespace (`poly_add_spec.ml`), and those of one parameter set have the
suffix `_44`, `_65` or `_87`.

The scripts are x86-64 versions of those in `../../arm/mldsa_native`.
`gen_layout.py` gives the same names as the AArch64 one wherever the code
has the same shape, and also names the jump tables of `switch`
statements, which gcc uses on x86-64 but not on AArch64.
`../proofs/mldsa_native/relative.ml`, which makes the proofs relative to
the statements of the callees, is the x86-64 version of the `relative.ml`
of the AArch64 proofs.

## Source of the code

The `binary` branch of mldsa-native only has binaries for AArch64, and its
`scripts/build-binaries` only builds for AArch64, so the code is
transcribed from the disassembly of a binary built in the same way on an
x86-64 Linux machine, except for the stack protector (see below).
Following `scripts/build-binaries` of the `binary` branch (commit
`3d3b1bdb`, whose C sources are those of commit `e71e3d6f`), as recorded
in `binaries/builds.json` there, the "multilevel" build
(`examples/multilevel_build`) was compiled in the nix shell `.#gcc12`
(gcc 12.3.0 and binutils 2.41, from nixpkgs 24.05) with `CFLAGS` set to
`-O2 -g -gdwarf-4 -gsplit-dwarf -fPIC -fno-stack-protector` and
`-fdebug-prefix-map` for the source directory, with `AUTO=0` and without
the native backends, using the target `mldsa_objs`. The object files were
archived with `ar rcsD`, in the sorted order of their paths, and the
archive was linked with
`ld -shared -Bsymbolic -soname libmldsa.so --whole-archive`, using the
version script `binaries/libmldsa.map`, to give `libmldsa.so`. The test
program of the example passes with it. In this build the code shared by
the three parameter sets is compiled once, with the namespace `mldsa_`,
and the rest once per parameter set, with the namespaces `mldsa44_`,
`mldsa65_` and `mldsa87_`. The binary has the same 192 functions, with the
same names, as the AArch64 binary of the same build.

| File (gcc 12.3.0)              | Binary                          |
|--------------------------------|---------------------------------|
| gcc12_O2/libmldsa.S            | multilevel/gcc12/O2/libmldsa.so |
| gcc12_O2/keccakf1600_permute.S | multilevel/gcc12/O2/libmldsa.so |

`gcc12_O2/keccakf1600_permute.S` is the code of `mldsa_keccakf1600_permute`
alone, with its table of round constants as a separate symbol. Its code is
that of `mlkem_keccakf1600_permute` in the x86-64 gcc 12 -O2 build of
mlkem-native, apart from the displacements of the table, and so its proof
is that of the x86-64 mlkem-native proofs, on the separate object,
transferred to the image (as for AArch64). `check_transcription.py`, also
from the x86-64 mlkem-native proofs, checks the separate object against
the binary:

```
python3 mldsa_native/check_transcription.py \
  mldsa_native/gcc12_O2/keccakf1600_permute.o \
  mldsa_native_keccakf1600_permute_gcc12_O2 \
  <build>/multilevel/gcc12/O2/libmldsa.so \
  mldsa_keccakf1600_permute \
  mld_KeccakF_RoundConstants mld_KeccakF_RoundConstants
```

The SHA-256 hash of the binary used is:

```
multilevel/gcc12/O2/libmldsa.so
  6e07fad018cdc3fb6edc9ca9be9753aa1c6e6a103e7075d32ebfd113eddeeecc
```

A binary built in another directory has a different hash, since the split
debug information records the paths of its files, but the contents of its
loaded segments are the same.

Unlike the AArch64 binaries, this one is built without gcc's stack
protector, which the nix shell otherwise enables. On x86-64 Linux the stack
protector reads its guard at offset 0x28 from the base of the FS segment,
in thread-local storage, rather than through the global offset table as on
AArch64, and the x86 model has no segment bases. With the stack
protector, 61 of the 192 functions, including 36 of the 42 API functions,
would copy the guard to the stack and check it before returning.

To regenerate the files of the build, in the `x86` directory:

```
python3 mldsa_native/gen_libmldsa_s.py \
  <build>/multilevel/gcc12/O2/libmldsa.so \
  mldsa_native_libmldsa_gcc12_O2 "gcc 12, -O2" \
  multilevel/gcc12/O2/libmldsa.so $PWD/../include \
  > mldsa_native/gcc12_O2/libmldsa.S
python3 mldsa_native/gen_layout.py \
  --name multilevel/gcc12/O2/libmldsa.so \
  <build>/multilevel/gcc12/O2/libmldsa.so \
  > proofs/mldsa_native/gcc12_O2/layout.ml
python3 mldsa_native/gen_proofs_mk.py gcc12_O2 \
  > mldsa_native/gcc12_O2/proofs.mk
```

`gen_libmldsa_s.py` assembles the transcription as the `Makefile` does and
checks that it is byte-for-byte the image of the binary, from address 0 to
the end of the read-only data, writing any instruction that the assembler
would encode differently, the NOPs and the instructions that refer to the
global offset table, which is outside the image, as `.byte`.
`libmldsa.ml` checks that the image has the size given in the layout file.

## The compiled code

Unlike the hand-written x86 code in `..`, the compiled code uses the
legacy SSE2 forms of vector instructions rather than the AVX2 ones, 8-bit
and 16-bit forms of scalar instructions, and the quadword string
operations `rep stos` and `rep movs`, which gcc uses to zero and copy
blocks of fixed size, all of which are in the x86 model in `../proofs`.
The aligned SSE loads and stores fault if the address of their operand is
not a multiple of 16, so the polynomials that the vectorized loops read
and write must be aligned, as they are in mldsa-native, whose polynomials
are aligned to 32 bytes.

The compiled code also uses the "red zone", the 128 bytes below the stack
pointer, which the System V ABI allows a function to use for data that is
not needed across calls, without moving the stack pointer, and calls the C
library through the procedure linkage table, whose entries jump to the
addresses in the global offset table. In each of the three
`prepare_domain_separation_prefix` functions, gcc compiles the `switch`
on the hash function to an indirect jump through a table of offsets in
the read-only data.

## What is proved

For each of the 192 functions of the image, `<f>_proof.ml` proves three
theorems about its code, as for the AArch64 code of mldsa-native:

 - `..._FULL`: `?f_events. !e args. H ==> ensures x86 (P /\ events = e)
   (Q /\ ?e2. events = APPEND e2 e /\ e2 = f_events <public args> /\
   memaccess_inbounds e2 R W) C`. This combines three properties.
   Correctness: the postcondition Q, with the functional specifications
   of `common/mldsa_native_*.ml`. Constant time: the trace of memory
   addresses and branch targets of the execution is a fixed function
   f_events of the public arguments only. Memory safety: all loads are
   within the regions R and all stores within W.
 - `..._CORRECT`: `!args. H ==> ensures x86 P Q C`, derived from FULL.
 - `..._SAFE`: FULL without Q, in the form of s2n-bignum's other safety
   theorems, derived from FULL.

FULL is the primary theorem because the callers that branch on the
results of their callees need both the values and the events of their
callees at once. These are signing, verification and the samplers.

The statements follow the AArch64 ones for the same functions, adapted
to the x86-64 calling convention of the System V ABI: on entry the
return address is at the stack pointer and the arguments after the sixth
are above it, and the function returns to that address with RSP 8 above
its value on entry. The function and its callees may write the N bytes
below the return address, `bytes(word_sub stackpointer (word N),N)`,
where N is the greatest depth below it that the code of the function and
its callees accesses, including the red zone.

`link.ml`, generated by `gen_link.py`, loads all the proofs and the FIPS
204 files (see below) in one session and closes the theorems of the API
functions and of the FIPS 204 files, so that they have no assumptions.

### The public arguments of the events

As for AArch64, besides addresses, lengths (of messages and contexts),
pc and the return address, the events may depend on exactly what the C
code declassifies (`MLD_CT_TESTING_DECLASSIFY`) or treats as public.
These are given as named HOL functions of the inputs:

 - the matrix A and anything derived from rho (rej_uniform,
   poly_uniform, poly_uniform_4x, polyvec_matrix_expand_eager,
   pk_from_sk's rho);
 - which nibbles the eta samplers accept (`mld_rej_eta_declass`,
   `mld_poly_uniform_eta_declass`, `mld_keypair_declass`);
 - the challenge seed c~ (poly_challenge and, per attempt, signing);
 - per signing attempt, the result of each norm check up to the first
   that fails and, if all pass, w0 - c s2 + c t0 and w1 packed
   (`mld_sign_attempt_declass`); also the number of attempts and the
   signature;
 - for verification, all its inputs (pk, the signature, the message);
 - for pk_from_sk, rho and the result of the check of the key.

### Hypotheses

 - The image is loaded at a 4096-aligned pc and fits in the address
   space. The written regions are disjoint from each other, from the
   inputs, from the image and from the return address on the stack.
 - No alignment of the stack pointer is assumed. 54 functions, whose
   local arrays mldsa-native aligns, align it to 32 bytes with
   `and rsp, -32`: the API functions other than verify_extmu and
   prepare_domain_separation_prefix, compute_pack_t0_t1 and the samplers
   that keep a Keccak state on the stack. For these N includes the up to
   31 bytes by which this lowers the stack pointer, and the proofs use
   `../proofs/utils/mldsa_native_realign.ml`. The five functions that
   use aligned SSE loads and stores on the polynomials that they are
   given (poly_add, poly_sub, poly_shiftl, poly_reduce and
   poly_power2round) assume them 16-aligned.
 - The direction flag is clear on entry, as the ABI requires, for the 83
   functions whose code, or that of their callees, uses `rep stos` or
   `rep movs` or calls the C library.
 - The C library functions satisfy the contracts of
   `../proofs/utils/mldsa_native_libc.ml` through their GOT entries:
   `memset_full_contract` (or `memset_ret_full_contract`),
   `memcpy_full_contract` and `randombytes_safety_contract`, as for
   AArch64. Each computes what it should, except that randombytes may
   return any bytes or fail. Its events are a function of its
   arguments. It reads only its arguments and a region (ea,el), and
   writes only its outputs.
 - Termination: the rejection samplers and SampleInBall loop until they
   have enough acceptable values, and the theorems assume that the SHAKE
   outputs have them. The predicates are `mld_rej_uniform_terminates`,
   `mld_rej_eta_terminates`, `mld_matrix_terminates`,
   `mld_keypair_terminates_XX`, `mld_poly_challenge_terminates` and
   `mld_sign_terminates_XX`. For ML-DSA-65 and -87 this includes the
   polynomial with nonce 255 that one call of `mld_poly_uniform_eta_4x`
   samples in vain during key generation.
 - Signing makes at most maxatt = (65535 - l) DIV l attempts (16382,
   13106 and 9361), and otherwise returns
   `MLD_ERR_SIGN_ATTEMPTS_EXHAUSTED`.

## Relation to FIPS 204

`../../common/fips204.ml` is a mathematical specification of ML-DSA
(FIPS 204), and `../../common/fips204_theory.ml` proves its properties.
Among them is the equivalence with the alternative way of checking the
low bits and computing the hints of Section 5.1 of the Round 3
Dilithium specification, which FIPS 204 permits and mldsa-native uses
(`MLDSA_SIGN_MU_ALT`). The lemmas of
`../proofs/utils/mldsa_native_fips204_*.ml` relate the specification of
the C code to FIPS 204, with no machine code involved:

 - `_ntt`: the NTT, its inverse and the Montgomery products as
   operations of R_q;
 - `_sample`: SHAKE, ExpandA, RejBoundedPoly, ExpandMask and
   SampleInBall;
 - `_round`: reduce32, Power2Round, Decompose, UseHint, the hints and
   the norm checks;
 - `_pack`: the bit packings, HintBitPack and HintBitUnpack;
 - `_keypair`: the keys of key generation are those of
   `mldsa_keygen_internal` (`MLD_FIPS204_KEYPAIR_44` etc.);
 - `_pk_from_sk`: the public key computed from a secret key is
   pkEncode(rho, t1) for skDecode(sk). The check passes iff s1 and s2
   are within [-eta,eta], t0 matches and tr = H(pk). In particular,
   pk_from_sk accepts the secret key that key generation makes and
   recovers its public key (`MLD_FIPS204_PK_FROM_SK_KEYGEN_44` etc.);
 - `_sign`: signing is FIPS 204 signing (`MLD_FIPS204_SIGN_44` etc.);
 - `_verify`: verification is FIPS 204 verification
   (`MLD_FIPS204_VERIFY_44` etc.).

These are the files of the AArch64 proofs, apart from the paths that
they load and two variables of `_sign` renamed because their names are
those of x86 registers. `../proofs/mldsa_native/gcc12_O2/fips204.ml`,
`fips204_sign.ml` and `fips204_verify.ml` derive the theorems for the
API functions from the lemmas and the CORRECT theorems. For each API
function and parameter set, a theorem `..._FIPS204` states the function
with the FIPS 204 functions, with its inputs and outputs as byte
strings: `mldsa_keygen_internal` and `mldsa_keygen` for key generation,
`mldsa_sign_internal`, `mldsa_sign_mu`, `mldsa_sign` and
`hash_mldsa_sign` for signing, and `mldsa_verify_internal`,
`mldsa_verify_mu`, `mldsa_verify` and `hash_mldsa_verify` for
verification. They have two further hypotheses:

 - Signing equals FIPS 204 signing when the fields of s2 in the secret
   key are at most 2 * eta. This holds for every key made by key
   generation. For a malformed key, FIPS 204 can accept an attempt that
   the code rejects (mldsa-native does not check the key when signing).
 - Signing returns the FIPS 204 signature when the code returns 0. When
   it returns `MLD_ERR_SIGN_ATTEMPTS_EXHAUSTED`, the first maxatt
   attempts of FIPS 204 signing are all rejected.
